THE IDEA

把查数与分析，放进同一段对话。

金融数据分散在不同表中，往往需要先找字段、写查询，再做图表。FinQuery 将这些步骤连接起来，让分析者用中文表达需求，并保留查看查询依据的入口。

01
问

快速找到想看的数据

面向行情研究者和业务分析者，支持筛选、排名、汇总与趋势查询。无需先掌握数据表名和 SQL 语法。

例如：某个交易日，涨幅最大的股票有哪些？
析

让结果变得容易理解

基于查询结果继续提问，生成文字解读与图表。也可以在一次提问中同时要求查询和绘图。

例如：把这份结果画成图，并解释主要差异。
存

保留可复用的分析素材

收藏结果表和常用字段，将历史结果加入工作区，为后续分析提供上下文；表格可导出，报告可保存为 Markdown 或通过打印保存 PDF。

例如：结合已收藏的结果，整理一份分析报告。
DATA FOUNDATION

从金融市场数据出发。

当前注册的 trade_data 数据库包含四类表。原始文件经数据管道整理成适合分析的 Parquet 文件，再由查询引擎读取。

02
stock_daily

股票日行情

价格、成交量与成交额、市值、资金流、行业分类及部分财务快照。

适合：股票筛选 / 行业比较
index_daily

主要指数日行情

上证指数、沪深 300 等指数的开高低收、成交量与成交额。

ETF 基金日行情

价格、成交、净值、复权因子、基金分类及基金份额。

适合：ETF 对比 / 分类分析

股票财务报表

资产负债、利润与现金流核心指标，按报告期和披露日期记录。

适合：财务指标 / 披露期分析

数据范围与最新日期以实际部署的数据为准；行情以日线为主。财报数据按披露记录组织，分析历史时点时需要区分报告期与披露日期。

BEHIND THE QUESTION

从一句中文，到有依据的回答。

系统先判断你需要什么，再选择对应的处理路径。大模型负责理解与规划，数据引擎负责执行实际查询。

03
问题 + 会话上下文 + 工作区先理解意图，再决定下一步
PATH A

直接回答

处理一般交流、能力询问，或先用一句话确认你真正想做什么。

例如：“你能查询哪些数据？”
依据当前用户可见的数据能力清单回答。
PATH B · 查询新数据

检索 → 规划 → 执行

1
找到相关字段结合关键词与语义检索，融合排序后重新评估相关性，选出适合回答问题的字段。
2
组织数据结构，生成 SQL依据表、字段和已声明的关系规划查询；必要时暂停，请用户补充会改变结果的条件。
3
通过受限工具执行只读查询检查 SQL 与访问权限，由 DuckDB 查询 CSV / Parquet 数据，最多返回 200 行。
4
返回表格与说明如果同时要求图表或报告，再用本轮结果进入分析路径。
PATH C

分析已有结果

基于当前或选定的历史结果进行解释、比较、总结，按需生成图表报告。

图表必须引用已有结果中的真实列。支持柱状、饼、折线、面积、散点、热力与 K 线图。
交互层 · Vue 3 + TypeScript + ECharts

组织对话、结果表和工作区，展示查询阶段进度与图表。

编排层 · FastAPI + LangGraph

连接模型、字段检索与上下文，支持澄清时暂停和继续。

执行层 · 进程内 MCP + DuckDB

MCP 是模型调用工具的统一接口；工具按权限提供，DuckDB 完成数据计算。

让权限贯穿查询过程

可见表、字段检索、工具发现与 SQL 执行都按用户权限限制；查询工具校验单条只读语句，要求明确列名。

让结果能够回看

前端展示生成的 SQL，后端保留工具调用与阶段日志。图表绑定结果来源，方便核对数据依据。

让失败有明确反馈

阶段错误会显式返回；SQL 失败后可在调用上限内修正。文字或图表生成失败时，保留已成功取得的表格。

01云端数据底座，支撑高效分析

把本地数据与查询计算迁到云端

对象存储 OSSAnalyticDB PostgreSQL

当前：当前不是一台可直接迁移的数据库服务器，而是本地 CSV / Parquet 文件，由进程内 DuckDB 临时注册成视图并查询。

对应产品与用法：建议在 OSS 中分开保存原始文件与整理后的 Parquet，记录来源、批次及版本清单，保留可回溯快照；由 AnalyticDB PostgreSQL 通过外表查询或导入内部表，向 FinQuery 返回结果。RDS 则承接第 04 项中的会话与任务状态。

验收关注：黄金查询结果一致、只读权限有效、云端延迟和成本符合目标。
AnalyticDB PostgreSQL · OSS 外表与存储 ↗OSS · 对象版本控制 ↗
02云端任务编排，驱动自动更新

让数据更新脱离本机计划任务

DataWorks · 开发与调度OSS · 原始层与整理层

当前：现有 Python 管道依次执行 convert → validate → compact，依赖本机目录与 Windows 定时任务。

对应产品与用法：将源文件接入 OSS 原始层，用 DataWorks 的 Python / Shell 节点编排“转换 → 校验 → 压实 → 发布”，配置周期调度与失败重跑；仅在校验成功后发布至 OSS 整理层，供分析引擎读取。

验收关注：校验失败不发布、重复运行不重复入库、可补跑和回溯、更新不依赖个人电脑。
DataWorks · 调度依赖与重跑 ↗DataWorks · Python 运行环境 ↗DataWorks · 自定义镜像 ↗

04云产品赋能，按业务场景定制

让会话与任务经得起重启

RDS PostgreSQL应用身份服务 IDaaS

当前：活动任务、认证令牌和澄清检查点在进程内；可选会话归档与收藏采用本地存储。

对应产品与用法：建议用 RDS PostgreSQL 存放任务、会话、收藏与检查点数据，利用其备份恢复能力；通过 IDaaS 的 OIDC 单点登录接入正式用户身份。

验收关注：重启后继续澄清、跨实例状态一致、权限隔离与恢复演练。

05云产品赋能，按业务场景定制

让更多问题同时得到处理

Serverless 应用引擎 SAE日志服务 SLSOpenSearch（按规模选用）

当前：查询通过后台线程运行，字段索引主要在本地计算；已有索引缓存和精简 SQL 重试上下文。

对应产品与用法：SAE 可托管后端镜像并按策略扩缩容；SLS 汇集日志与观测数据，帮助定位慢阶段。字段量增长后，可评估 OpenSearch 的文本、向量混合检索及条件过滤。

验收关注：高分位响应时间、并发量、单次成本与检索质量；扩容不等于模型额度增加。
SAE · 应用托管与弹性 ↗SLS · 日志与可观测 ↗OpenSearch · 混合检索 ↗
