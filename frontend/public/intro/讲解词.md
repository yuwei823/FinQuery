# FinQuery Studio 项目介绍讲解词

> 适合向第一次了解项目的听众介绍。建议时长约 7–9 分钟，可按现场时间跳过交互演示中的一两个场景。方括号内容是讲解提示，无需念出。

## 开场｜先说明今天要讲什么（约 20 秒）

大家好，今天介绍的是 FinQuery Studio，一个面向金融市场数据的中文问数与分析应用。接下来我会从使用者的角度，介绍它能解决什么问题、目前可以查询哪些数据、一次提问在系统里经历哪些步骤，以及如果继续建设，可以怎样逐步接入阿里云产品。

我做 FinQuery，主要是想把过去在数据平台上的经验延伸到 AI 应用里，亲手跑通一个 Data Agent 项目。数据产品正在从传统报表和 BI 向自然语言交互发展，我想验证：用户能不能直接用自然语言提出问题，系统再结合数据结构和业务意图，安全、可靠地完成查询与分析。

所以我把场景落在金融市场数据上。目标用户可能不熟悉 SQL，但会有查询股票、指数、ETF 和财务数据的需求。FinQuery 是我独立设计并公开部署的自然语言问数应用；我负责产品流程、系统方案和工程验证，并借助 AI 工具完成代码开发。

这个项目让我从数据平台研发进一步走到了 AI 应用方案的完整链路，也让我实际处理了自然语言理解、Schema 映射、SQL 安全和结果呈现之间的衔接问题。它目前是个人项目和公开演示环境，重点是验证方案与端到端链路，并不代表已经在企业生产环境完成部署。

## 首页｜用自然语言读懂金融数据（约 35 秒）

[停留在页面首屏，指向示意图。]

FinQuery 希望把“我想了解一个金融问题”和“拿到一份可以继续分析的数据结果”连接起来。使用者用中文描述需求，系统尝试理解问题、查找相关字段、执行查询，并把结果整理成表格、图表或文字报告。

右边的图是界面示意，不是真实市场行情。核心体验是：不必先熟悉每一张数据表，也不必手写 SQL，就可以从一个业务问题开始分析。对于有经验的使用者，页面还保留了查看 SQL 和查询过程的入口。

## 项目概览｜把查数和分析放进同一段对话（约 45 秒）

[滚动到“把查数与分析，放进同一段对话”。]

传统的数据分析通常要先找表和字段，再写 SQL、看结果，最后另开工具做图或报告。FinQuery 把这些动作放到同一条对话流程里。

第一类是查询新数据，例如筛选股票、做排名或计算趋势。第二类是拿已经得到的结果继续追问、比较，或者整理成报告。第三类是把查询结果收藏起来，之后放进工作区继续分析。这里的重点是让分析过程连续起来，不是让模型凭空给出一段看似合理的结论。

## 业务价值｜从痛点、指标到方案（约 1 分 40 秒）

[可以在项目概览之后、交互演示之前讲；若听众主要是业务负责人，建议保留本节。]

在讨论技术架构之前，先说业务为什么需要这样的工具。第一个痛点是分析链路长：业务人员提问题之后，往往还要找数据同事确认表和字段、等待 SQL 查询、再把结果整理成图表。第二个痛点是数据门槛高：会使用金融术语，不一定熟悉每个数据源的字段名称和查询规则。第三个痛点是分析过程难以复用：一个问题的口径、SQL 和结果说明可能分散在聊天、脚本和表格里。FinQuery 尝试把问题理解、查询执行和结果解释连接起来，并保留 SQL、查询阶段和可收藏结果，减少这些环节之间的往返。

这些是我们从产品流程中识别的待验证痛点。它们是否真实影响目标用户、影响多大，需要通过用户访谈和试点数据确认，不能仅凭功能本身得出业务收益结论。

为了判断是否有改善，可以先定义一组指标，并在试点前采集基线：

- **问题到结果耗时**：从用户提交问题，到表格或报告成功呈现的时间；同时观察中位数和较慢请求的高分位耗时。
- **首次查询成功率**：首次 SQL 执行成功的数据库查询数，除以数据库查询总数；另行跟踪经过修正后最终成功的比例。
- **结果正确率**：在有人工确认的业务测试集上，与黄金结果按字段、数值容差和口径逐项比较后通过的比例。
- **字段召回率**：问题需要的字段中，被检索结果找回的比例。这项已有离线评估入口，但不代表线上查询准确率。
- **澄清完成率**：系统发起澄清后，用户补充信息并最终得到可用结果的比例。
- **单次完成成本与数据新鲜度**：统计一条成功问答消耗的模型与云资源费用，并记录新数据发布到可查询之间的延迟。

目前代码提供部分测试与评估工具，但这里列出的指标目标值、线上基线和试点收益都还没有测定。应该先用一批代表性问题建立基线，再决定优化重点。

方案选型可以按规模分三步。第一步，若目标是验证产品价值，继续使用现有 DuckDB 和 Parquet，补齐业务问题集、指标口径和失败记录，先以较低迁移成本确定质量基线。第二步，若目标是稳定的云端每日更新和多人访问，再把文件与数据管道迁到 OSS 和 DataWorks，并将任务、会话与检查点放入共享存储。第三步，只有当实际扫描量、并发、响应时间或跨库需求达到现有架构的边界，再评估 AnalyticDB PostgreSQL、SAE、OpenSearch 等云端能力。选择时要同时比较查询兼容性、数据规模、并发要求、团队运维能力、权限方案和预期成本，不建议仅因为某个产品可用就整体替换。

主要风险包括金融指标或复权口径理解错误，模型生成的查询与用户意图不一致，数据更新延迟或结果被行数上限截断，以及账户权限配置不当。迁到云端后，还需管理访问凭证、网络边界、供应商依赖和持续费用。对应的控制方法是建立经业务确认的指标字典和黄金案例，在发布前校验数据、对查询结果做权限与正确性检查，并监控调用失败、响应时间、资源费用和数据更新时间。任何数字型业务收益都应在试点中测量后再对外承诺。

如果这些指标通过试点验证，预期的业务收益可以表述为：常见问题更快获得初步数据结果，减少查询需求在业务与数据团队之间的反复转换；分析过程和口径更容易复核与复用；数据团队可把更多时间投入新的数据接入和复杂分析。它们是待验证的收益目标，不是本项目已经测出的提升比例。

## 交互演示｜问题如何变成结果（约 1 分 20 秒）

[依次点选三个场景。先选择“查询新数据”，播放处理过程。]

第一个场景是查询新数据。比如，我们想知道某个交易日涨幅靠前的股票。系统需要确认日期、指标和返回数量，找到对应字段，再组织查询并呈现结果。实际运行中，用户可以查看 SQL、收藏结果，或接着提出相关问题。这里的演示是本地交互示意，不会真的连接模型或查询数据库。

[选择“查询并生成图表”，播放处理过程。]

第二个场景是查询的同时要求图表。系统先从数据库取得真实结果，再根据结果里的日期和开高低收字段生成 K 线图配置，并附上解读。图表要使用查询结果中实际存在的列，生成图表的过程不会另外编造行情数据。

[选择“分析已有结果”，播放处理过程。]

第三个场景是基于已有结果继续分析。此时系统读取对话或工作区中已有的结果，再生成说明或报告。它不需要为了写报告重新查询一次数据库。报告可以导出为 Markdown，也可以通过浏览器打印保存为 PDF。

## 数据范围｜目前从哪些数据出发（约 50 秒）

[滚动到四张数据卡片。]

当前接入的主要是四类中国金融市场数据。股票日行情包括价格、成交、市值、资金流、行业以及部分财务快照；指数日行情记录主要指数的每日开高低收和成交情况；ETF 日行情包括价格、净值、分类和份额等字段；财务报表则按报告期和披露日期记录资产负债、利润和现金流指标。

这些表主要支持日频行情查询和基于历史结果的分析。日期覆盖和最新数据会随着实际部署的数据而变化。特别是财报，分析历史时点时要区分报告期和实际披露日期，不能把后来才披露的信息当成当时已知的信息。

页面下方的数据管道展示了数据进入系统之前的处理：检查源文件、增量转换、校验，再压实并更新。校验通过后再发布，是保护下游查询结果质量的重要步骤。

## 工作原理｜从一句话到有依据的回答（约 1 分 30 秒）

[滚动到三条处理路径，先指向入口，再从左向右介绍。]

每个问题首先会结合当前对话和工作区进行理解，然后进入三条路径之一。

如果是一般交流、能力咨询，或目前缺少足以确定需求的信息，系统会直接回答或进行确认。它不会假装已经查过数据。

如果用户要查询新数据，系统先检索与问题相关的字段。它结合关键词匹配和语义检索，再把候选结果融合排序，形成一份只包含相关表和字段的结构说明。之后查询智能体依据这份结构生成 SQL，通过 MCP，也就是模型调用数据工具的统一接口，把查询交给 DuckDB 执行。

执行环节有明确限制：一次只执行一条只读查询，必须显式选择字段，并检查数据表和访问权限；结果最多返回 200 行。如果关键条件确实会改变结果，但无法从上下文和数据结构里判断，系统可以暂停查询，让用户确认后继续。

第三条路径是分析已经存在的查询结果。它可以生成文字总结和图表。报告中的图表要引用现有结果里的字段，因此分析可以回到实际数据核对。

[指向下方三项安全与回看说明。]

这套设计希望让权限和数据依据贯穿查询过程：权限会影响用户能看到的表和能调用的工具；结果保留生成 SQL 和阶段信息；如果图表或文字生成失败，已经成功拿到的查询表仍可以保留下来。

## Scale Up｜从本地原型走向云端能力（约 2 分 30 秒）

[说明当前这部分是建议，不是已部署的云架构。]

接下来是可提升的内容。下面讨论的是基于当前代码提出的方案，页面标注的阿里云产品还没有接入，也没有执行数据迁移。我们把最直接影响云端数据链路的两项放在最前面。

### 01 云端数据底座，支撑高效分析

当前的数据不是一台可以直接迁走的数据库服务器，而是本地 CSV 和 Parquet 文件，由 DuckDB 在应用进程中注册后执行查询。建议把原始文件和整理好的 Parquet 分层放到对象存储 OSS，并记录数据来源、批次和版本清单；再由 AnalyticDB PostgreSQL 通过 OSS 外表读取，或把数据导入数据库内部表，最终把查询结果返回给 FinQuery。

这里需要开发新的查询适配层。DuckDB 和云端数据库的 SQL 方言、类型、权限和运行方式需要逐项核对，再用现有查询案例验证结果一致。OSS 负责存放文件，SQL 计算由分析引擎承担。

### 02 云端任务编排，驱动自动更新

当前数据更新脚本按“转换、校验、压实”的顺序运行，由本机 Windows 计划任务启动。上云后，可以把源文件放在 OSS 原始层，用 DataWorks 编排 Python 或 Shell 任务，按顺序完成转换、校验、压实和发布，再把整理后的 Parquet 写入 OSS 整理层。

校验通过后再发布，并配置失败重跑和历史版本，数据更新就能脱离个人电脑。要注意的是，如果上游文件仍然只在本机，云上任务仍然拿不到数据；还要增加上传或云端采集这一步，并适配本地路径、增量清单和 Python 依赖。

### 03 衡量回答质量

项目已有单元测试、黄金 SQL 结果快照和字段召回评估。下一步可以用百炼的评测能力，比较不同模型或提示词对回答的影响，并加入人工评价。但应用的查询是否正确，仍要检查实际 SQL 结果；权限、澄清和报告数字也需要项目自己的测试。

### 04 持久化会话与任务

目前有些活动任务和澄清状态保存在进程内。本机重启或多实例运行前，可以用 RDS PostgreSQL 等共享数据库保存会话、收藏和检查点，并通过 IDaaS 的 OIDC 单点登录接入正式身份。接入后仍要由 FinQuery 负责具体数据表和任务的业务权限。

### 05 提升并发和运行观测

应用可以评估部署到 SAE，日志和阶段耗时接入 SLS。这样能帮助运维观察请求在哪一步变慢，并根据实际负载调整应用实例。扩大实例数量前，要先把会话和任务状态迁到共享存储；任务队列、取消、超时和模型调用额度仍需专门设计。

### 06 统一金融指标和时间定义

DataWorks 的数据建模可以帮助管理数据标准、维度和指标定义。FinQuery 还需要把交易日、收益率、复权方式、财报披露时点和字段关系这些金融规则明确下来，并同步到查询 Schema 和验证案例。云产品提供管理工具，具体业务口径需要与使用者共同确定。

### 07 扩展到多数据库分析

现在可以配置多个数据库，但一次问题跨多个库仍未完成。AnalyticDB PostgreSQL 的部分联邦查询能力可以作为执行底座之一；FinQuery 仍要实现任务拆分、实体映射、各库独立权限和结果合并。接入前也要核对实例模式和网络条件。

### 08 展示数据范围与新鲜度

当前查询最多返回 200 行，分析上下文也有行数限制。OSS 可以存储完整导出文件、报告和数据版本；FinQuery 页面还需要清楚标注结果是否截断、分析覆盖的日期，以及数据最后更新时间。用户看到的分析范围和下载范围都应明确。

[指向底部“仍需项目自行实现的能力”和阶段建议。]

这部分可以概括为：云服务能提供存储、调度、计算、身份和观测等基础能力；FinQuery 还需要把这些能力连接到金融语义、问数流程和准确性验证。落地顺序上，先迁数据文件与更新任务并保留 DuckDB 做结果对照；再处理身份、会话与应用运行；最后根据实测数据决定是否更换查询引擎和扩展检索服务。

## 结束｜回到项目价值（约 20 秒）

[滚动至页面结尾。]

总结一下，FinQuery Studio 尝试把中文提问、金融数据查询和结果分析放进同一段可回看的工作流。它目前已有单库问数、结果分析、图表报告和增量数据整理能力；接下来的提升重点，是让数据更新和查询引擎能够支撑云端运行，同时把金融口径、权限、质量验证和状态恢复打磨完整。
